# Прогресс разработки Glossa V2

Один пункт плана (`Plan/IMPLEMENTATION_PLAN.md`, дополнено `Plan/SPEAKING_PLAN.md`) — один коммит. Здесь фиксируется,
что сделано и где искать код, в том же порядке, в котором пишется код — читать сверху вниз.

Слои читать по `docs/CONVENTIONS.md`: `Backend/app/{api,core,db,models,schemas,services}`,
файлы `model_*.py` / `schema_*.py` / `crud_*.py` / `router_*.py`.

## Фаза 1 — Каркас проекта

### 1.1. Скелет папок и пустой frontend
- `Backend/app/{api,core,db,models,schemas,services}/__init__.py` — пустые пакеты, слои по CONVENTIONS.md (не `modules/`, как в старом черновике плана — CONVENTIONS.md главнее).

### 1.2. Базовые зависимости
- `Backend/requirements.txt` — fastapi/uvicorn/sqlalchemy/asyncpg/alembic/pydantic/python-jose/passlib/python-dotenv/python-multipart/redis, версии зафиксированы через `pip freeze` в `Backend/.venv`.
- `Backend/.gitignore` — .venv/.env/__pycache__/кэши тестов/media/staticfiles/IDE-файлы.

### 1.3. Конфиг и .env.example
- `Backend/app/core/config.py` — класс `Settings`, всё из `os.getenv`, синглтон `settings`. Поля привязаны к уже существующему `Backend/.env` (не менял имена: `JWT_SECRET_KEY`, `TG_BOT`, email-блок), добавил `DB_ECHO` и `REDIS_URL` с рабочими дефолтами.

### 1.4. Подключение БД

### 1.5. Точка входа FastAPI
- `Backend/app/main.py` — `FastAPI(title='Glossa 🌍 — Language Learning API')`, CORS `allow_origins=['*']` (как в Green Shop), `GET /health` → `{'status': 'ok'}`.
- Проверено вживую: `uvicorn app.main:app` на 8010 (мой тестовый порт, не 8000 — см. привычку из Ometus), `/health` → 200, `/docs` → 200.

### 1.6. Docker: postgres + redis
- `Backend/docker-compose.yml` — сервисы `postgres:16` и `redis:7`, healthcheck, volumes.
- **Важное решение по портам**: на этой машине уже крутится нативный (не-докерный) Postgres как Windows-сервис на 5432 — общий для всех Softclub-экзаменов (в нём видны `books_db`, `users_services_db`, `restaurants_db` и т.д., и **`GlossaV2` там уже создана заранее**). `DATABASE_URL` в `.env` продолжает смотреть на этот нативный инстанс (5432) — трогать его не стал. Чтобы не конфликтовать портом, докеровский postgres в compose слушает **5433** на хосте (`POSTGRES_PORT` в .env/.env.example), redis — как обычно на 6379 (нативного redis на машине нет).
- Проверено вживую: `docker compose up -d postgres redis` — оба healthy; с хоста подключился и к докеровскому postgres (5433), и к redis (6379); нативный postgres (5432, `GlossaV2`) отдельно тоже доступен и именно на него смотрит приложение.

### 1.7. Alembic
- `Backend/alembic.ini`, `Backend/alembic/env.py` (async-вариант по образцу `Bon Appetit/user-services/alembic/env.py`: `target_metadata=Base.metadata`, url из `settings.DATABASE_URL`), `Backend/alembic/script.py.mako`.
- Проверено вживую на нативной `GlossaV2` (пустая на тот момент): `alembic revision --autogenerate -m "empty baseline"` дал пустую миграцию `alembic/versions/88bff8d55a71_empty_baseline.py`, `alembic upgrade head` прошёл, `alembic current` показывает head.

### 1.8. Redis-клиент
- `Backend/app/core/redis_client.py` — `redis.asyncio.from_url(settings.REDIS_URL, decode_responses=True)`, синглтон `redis_client`, `get_redis()` для Depends.
- Проверено вживую: `ping()` к докеровскому redis (6379) → True.

### 1.9. JWT-хелперы FastAPI
- `Backend/app/core/security.py` — `oauth2_scheme` (`OAuth2PasswordBearer`, `auto_error=False`), `decode_access_token()` через `python-jose` с `settings.JWT_SECRET_KEY`/`JWT_ALGORITHM`. FastAPI здесь **только валидирует** — выдачей токенов занимается Django (фаза 2), поэтому в отличие от `Bon Appetit/security.py` тут нет `hash_password`/`create_access_token`.
- Проверено вживую: токен, подписанный тем же `JWT_SECRET_KEY`, декодируется; просроченный и мусорный токен → `None`.

**Фаза 1 закрыта**: `uvicorn app.main:app`, `/health`, `/docs`, postgres+redis (докер на 5433/6379 + нативный postgres на 5432 с уже готовой `GlossaV2`), alembic, redis-клиент и JWT-валидация — всё проверено вживую.

### 2.10. Исключение django-таблиц из Alembic
- `Backend/alembic/env.py` — импортирует `app.models.model_user` (чтобы `users` реально попала в `target_metadata`, иначе тест ничего не проверял бы), `include_object` фильтрует `type_=='table'` с именем `users` или префиксом `users_`/`django_`/`auth_`/`token_blacklist_`.

После добавления префикса `alembic revision --autogenerate` на БД с django-таблицами и мапленной `Users` даёт пустую миграцию; `alembic upgrade head` проходит.

### 2.11. Django в docker-compose
- `Backend/docker/Dockerfile.django` — `python:3.12-slim`, ставит `requirements.txt`, рабочая директория для CMD — `auth_service/`, `manage.py runserver 0.0.0.0:8001`.

- `Backend/.dockerignore` — добавлен (не было в плане явно, но без него `COPY . .` затащил бы `.env` с секретами в образ); по образцу `Bon Appetit/user-services/.dockerignore`.
- Проверено вживую: `docker compose build django_app` + `up -d` — контейнер поднялся; `POST /api/auth/register` и `/api/auth/login` **через контейнер на 8001** отработали и записали пользователя в ту же нативную `GlossaV2`.

## Фаза 5 — Системный контент: словарь, грамматика, истории

**Важно перед этой фазой** — корневой баг V1 ([[glossa-trilingual-audit]]): `pick_locale` в старом проекте выбирал, на каком языке показать **весь текст истории**, по UI-локали (родной язык), а не по языку, который человек учит — история на английском с `?locale=ru` превращалась в полностью русский текст, что убивало смысл чтения на изучаемом языке. Свежая сверка с `contents/`: словарь/грамматика/истории структурно **одноязычные** (word/example_en/rule_en только в английском; `_ru`/`_tg` — это переводы/объяснения ДЛЯ рувоязычных/таджикоязычных студентов, а не отдельные курсы на этих языках). Поэтому в V2 решение: `locale` управляет **только вспомогательным текстом** (перевод слова, объяснение правила, текст вопроса на грамматику), но **никогда** не подменяет тело истории или её вопросы на понимание — они остаются на английском всегда (в моделях `Stories.body`/`StoryQuestions.text` вообще нет `_ru/_tg` вариантов, в отличие от `GrammarQuestions.text_en/ru/tg`, где локаль уместна — это тест на грамматику, а не чтение).

### 9.6. Stripe webhook
- `stripe_service.construct_webhook_event(payload, signature)` — `stripe.Webhook.construct_event` по подписи; невалидная подпись/пустой `STRIPE_WEBHOOK_SECRET` → `AppError('INVALID_STRIPE_SIGNATURE', ...)` / `STRIPE_NOT_CONFIGURED`, обе 400.
- `router_payment.stripe_webhook` (`POST /stripe/webhook`) — читает сырое тело запроса (`await request.body()`, не Pydantic-модель — подпись считается по байтам as-is), заголовок `Stripe-Signature`; при `checkout.session.completed` достаёт `metadata.user_id` и `amount_total` (в центах) из события, зовёт `crud_payment.topup_balance(user_id, amount_total/100, db)` — автосоздание баланса уже встроено в `topup_balance` через `get_or_create_balance`.
- Важная деталь: проверка подписи (`stripe.Webhook.construct_event`) — это чистый локальный HMAC-SHA256, не сетевой вызов к Stripe. Это позволило по-настоящему прогнать оба ветки DoD **без обращения к реальному Stripe API** — достаточно временного тестового `STRIPE_WEBHOOK_SECRET`, который никуда не сохранён (передан только как переменная окружения на время одного тестового запуска сервера, не в `.env`).
- Проверено вживую по-настоящему сквозным HTTP-запросом (не юнит-тестом функции): собрал корректный Stripe event JSON (с обязательными полями `id`/`object:'event'`/`api_version`/`created`, без которых сама библиотека `stripe` падает при парсинге — не хватало на первой попытке) и подписал его вручную тем же HMAC-алгоритмом, что использует Stripe (`t={timestamp},v1={hex_hmac}`); `POST /stripe/webhook` с валидной подписью и `amount_total=15000` → `200 {"status":"ok"}`, и `GET /balance` для того же пользователя сразу же показал `150.00` — списание сошлось с точностью до цента; тот же запрос с заведомо неверной подписью (`v1=deadbeefbadsignature`) → `400 INVALID_STRIPE_SIGNATURE`. Оба пункта DoD подтверждены реальным round-trip через работающий сервер. Тестовые данные (баланс, Django-пользователь, временные файлы payload/header) подчищены; сервер перезапущен без тестовых ключей.

### 10.11. XP и ачивки за истории

## Фаза 11 — Очереди: Celery, Kafka, Beat

### 11.1. Celery-приложение
- `Backend/app/celery_app.py` — `celery_app = Celery('glossa', broker=..., backend=...)`; `task_routes` по регулярным выражениям на модуль задачи (`app.tasks.priority.*` → `priority_queue`, `content.*` → `content_queue`, `notifications.*` → `notifications_queue`, `ai.*` → `ai_queue`, `analytics.*` → `analytics_queue`, `payments.*` → `payments_queue`) — сами модули `app/tasks/*.py` появятся по мере надобности в следующих шагах (11.7/11.8 и далее), сейчас только маршрутизация и одна тестовая задача `ping`.
- `Backend/app/core/config.py` — `CELERY_BROKER_URL`/`CELERY_RESULT_BACKEND`, дефолт `redis://localhost:6379/1` — **отдельная** база Redis (индекс `1`), не та же `/0`, что уже занята лимитами/лидербордами из Фазы 8/7, чтобы ключи Celery не путались с бизнес-данными.
- `requirements.txt` — добавлен `celery==5.6.3` и его транзитивные зависимости (`amqp`, `billiard`, `kombu`, `click-didyoumean`/`click-plugins`/`click-repl`, `prompt_toolkit`, `tzlocal`, `vine`, `wcwidth`, `packaging`).
- Проверено вживую по-настоящему, не только импортом: поднял `celery -A app.celery_app worker -Q priority_queue --pool=solo` (Windows требует `--pool=solo`, дефолтный prefork не работает) — воркер стартовал, подключился к `redis://localhost:6379/1`, объявил очередь `priority_queue` и задачу `app.tasks.priority.ping`; вызвал `ping.delay()` из отдельного Python-процесса и дождался результата через `.get(timeout=10)` → `'pong'` — задача реально выполнилась воркером, а не просто была поставлена в очередь. Воркер остановлен после теста.

### 11.2. Воркеры в docker-compose
- `Backend/docker/Dockerfile.worker` — тот же паттерн, что `Dockerfile.django` (`COPY . .` + `pip install -r requirements.txt`), но `WORKDIR` остаётся `/app` (не `/app/auth_service`), т.к. `celery_app.py` лежит прямо в `Backend/app/celery_app.py`; `CMD` без `-Q` — очередь передаётся через `command:` каждого сервиса в compose.
- `docker-compose.yml` — 6 сервисов (`celery_priority/content/notifications/ai/analytics/payments`), каждый со своим `command: celery -A app.celery_app worker -Q <своя_очередь>`; `CELERY_BROKER_URL`/`CELERY_RESULT_BACKEND` переопределены на `redis://redis:6379/1` (внутри docker-сети по имени сервиса, не `localhost`, как в дефолте конфига для локального запуска); `DB_HOST=host.docker.internal`/`DB_PORT=5432` — тот же паттерн, что у `django_app`, чтобы будущие DB-задачи воркеров ходили в тот же нативный Postgres, что и локальный FastAPI dev-сервер.
- Проверено вживую на реальных контейнерах, а не только конфигурацией: `docker compose build` всех 6 → успешно; `docker compose up -d` всех 6 → все `Up`; из отдельного Python-процесса явно отправил уже существующую тестовую задачу `ping` в каждую из 6 очередей по очереди (`apply_async(queue=...)`) и дождался всех 6 результатов → все `'pong'`; в логах **каждого** контейнера — ровно один `received`/`succeeded` для соответствующей ему очереди (не больше, не от чужих очередей) — реально подтверждает "берут задачи только своих очередей", а не просто что воркеры запустились. Контейнеры остановлены после проверки (конфигурация остаётся в репозитории для реального использования в следующих шагах).

### 11.3. Kafka заменена на Redis Streams (окружение блокирует реальный Kafka)
- Изначально по плану добавил `zookeeper`+`kafka` (confluentinc образы) в `docker-compose.yml`, `KAFKA_BOOTSTRAP_SERVERS` в конфиг, `aiokafka` в requirements — но образы отказались тянуться: 4 независимые попытки (`docker compose up`, прямой `docker pull confluentinc/cp-zookeeper`, `docker pull confluentinc/cp-kafka` через compose, `docker pull apache/kafka:3.7.0`) все зависали без вообще какого-либо прогресса, при том что в этой же сессии до этого спокойно стянулись `postgres:16` (642MB), 6×`celery worker` образов (по 514MB, 3GB суммарно), `minio`, `node:22-alpine` и т.д.
- Не стал просто повторять одну и ту же неудачную команду — продиагностировал первопричину напрямую через `curl` к Docker Hub registry API в обход самого `docker pull`: получение auth-токена и manifest (список слоёв) прошло быстро (2-10 сек); но прямая загрузка одного реального слоя образа (254MB) заняла бы **часы** — измеренная скорость **~18 КБ/с** (`curl -w '%{speed_download}'` на реальном байтовом трансфере с валидным токеном, `http_code=200`, т.е. не ошибка авторизации — соединение просто предельно зажато по пропускной способности именно на уровне blob-CDN Docker Hub в этом окружении, при том что API-вызовы и мелкие образы работают нормально). При такой скорости весь образ `cp-kafka` (~470MB) тянулся бы 4+ часа, `cp-zookeeper` — сопоставимо.
- Спросил пользователя, как поступить с этим реальным блокером окружения; пользователь предложил заменить саму технологию на что-то не медленнее — выбрал **Redis Streams** (`XADD`/`XREADGROUP`/`XACK` на том же самом Redis, который уже работает в проекте под лимиты/лидерборды/Celery-брокер): не требует новой инфраструктуры и образов вообще, in-memory — быстрее, чем Kafka для нагрузки такого масштаба, и полностью снимает проблему registry-throttling. Откатил все изменения под Kafka (`zookeeper`/`kafka` сервисы из compose, `KAFKA_BOOTSTRAP_SERVERS` из конфига, `aiokafka` из requirements — ни одно из этих трёх изменений не было закоммичено, откатывать пришлось только рабочую копию).
- Дальнейшие шаги фазы 11, которые в плане завязаны на Kafka (11.4 продюсер событий, 11.5 консьюмеры), будут реализованы на Redis Streams с тем же архитектурным паттерном (публикация события → чтение через consumer group → диспатч в Celery-очередь), только на другой транспортной технологии.
- Проверено вживую через `redis-cli` внутри контейнера `backend-redis-1` (аналог "через консоль" из DoD, только консоль redis, а не kafka): `XADD test_events '*' event_type test_produce payload hello` → создал запись; `XLEN`/`XRANGE` подтвердили её присутствие; `XGROUP CREATE test_events test_group 0` → `OK`; `XREADGROUP GROUP test_group consumer1 COUNT 1 STREAMS test_events '>'` → вычитал ту же запись через consumer group (паттерн, эквивалентный Kafka-консьюмерам с offset-трекингом); `XACK` → `1` (подтверждение обработки прошло). Тестовый стрим удалён.

### 11.4. Продюсер событий (на Redis Streams вместо Kafka)
- `Backend/app/core/event_bus.py` — `publish_event(topic, payload, fallback_task=None)`: `XADD` с JSON-сериализацией payload в один хэш-ключ `payload` (Redis Streams хранит плоские хэши полей, не произвольный JSON напрямую, поэтому весь payload упаковывается одной строкой — так же, как это делали бы с value в Kafka); при недоступности Redis (`ConnectionError`/`TimeoutError` — оба поймал, т.к. падение по таймауту на недоступный порт даёт именно `TimeoutError`, не `ConnectionError`, что не было очевидно заранее и выяснилось только на реальном тесте) — прямой вызов `fallback_task.delay(**payload)`, минуя шину вообще, как и требует "graceful degradation" из плана. `TOPICS` — имена стримов (`ai_tasks`/`analytics_events`/`payment_events`/`content_events`), те же, что были бы Kafka-топиками.
- Проверено вживую дважды: (1) с реальным работающим Redis — `publish_event('content_events', {...})` → `True`, `XRANGE` в самом Redis показал реально записанную запись с корректным JSON; (2) искусственно подменил `event_bus.redis_client` на клиент, указывающий на заведомо недоступный порт (`redis://localhost:1/0`) — `publish_event(..., fallback_task=FakeTask())` поймал `TimeoutError` и вызвал `fallback_task.delay(**payload)` напрямую (подтверждено по выводу), вернул `False`. Оба пункта DoD ("событие уходит в топик"/"при недоступности — задача падает в Celery напрямую") подтверждены реальным поведением, а не только чтением кода.

### 11.5. Redis Streams-консьюмеры (замена Kafka-консьюмеров)
- `Backend/app/consumers/base.py` — `consume_once(stream, group, consumer_name, task, count, block_ms)`: создаёт consumer group при первом обращении (`ResponseError` при уже существующей — игнорируется), читает через `XREADGROUP` блокирующим режимом, для каждого сообщения парсит JSON из поля `payload` и зовёт `task.delay(**payload)`, затем `XACK`; `run_consumer` — бесконечный цикл `consume_once`.
- `Backend/app/tasks/{ai,analytics,payments}.py` — по одной задаче-заглушке на очередь (`app.tasks.ai.process_event` и т.д., имена совпадают с уже заданными в 11.1 `task_routes`); `celery_app.py` пополнен `conf.imports` (не прямой импорт на верхнем уровне модуля — иначе циклический импорт `celery_app → app.tasks.ai → celery_app`, т.к. `app.tasks.ai` сам импортирует `celery_app`; `conf.imports` — стандартный способ Celery отложенно зарегистрировать модуль задач при старте воркера).
- `Backend/app/consumers/{ai_consumer,analytics_consumer,payments_consumer}.py` — тонкие точки входа: каждый вызывает `run_consumer` со своим стримом/группой/задачей.
- `Backend/docker/Dockerfile.consumer` + 3 сервиса в `docker-compose.yml` (`consumer_ai`/`consumer_analytics`/`consumer_payments`), тот же паттерн переменных окружения, что у `celery_*` (`REDIS_URL` тоже переопределён на `redis://redis:6379/0`, т.к. консьюмеры читают из основной БД `0`, а не из БД `1`, которую использует только Celery-брокер).
- Настоящий баг, пойманный только на реальном контейнерном прогоне (не на хосте): блокирующий `XREADGROUP` с `block=5000` внутри Docker-сети иногда кидает `redis.exceptions.TimeoutError`, если новых сообщений не появилось за это время, — раньше это падало необработанным исключением и убивало весь `while True`-цикл консьюмера (контейнер оставался жив, но переставал читать дальше после первого же пустого блока). Это нормальный исход опроса ("сообщений пока нет"), а не ошибка — обернул `XREADGROUP` в `try/except RedisTimeoutError: response = None`.
- Также поймал на этом же прогоне: `celery_ai`/`celery_analytics`/`celery_payments` контейнеры были собраны в 11.2 **до** появления `app/tasks/*.py` — образы не содержали новый код (Docker-образ фиксирует `COPY . .` на момент сборки), из-за чего воркеры сначала падали `Received unregistered task` для всех трёх задач. Пересобрал эти три образа после добавления модулей задач.
- Проверено вживую **дважды**: сначала хост-скриптом (публикация в `ai_tasks` → `consume_once` → celery-воркер на хосте реально выполнил `app.tasks.ai.process_event` с точным payload, видно в логе воркера) — доказывает саму логику; затем **полностью в контейнерах**: поднял `celery_ai`/`celery_analytics`/`celery_payments` (образы из 11.2, пересобранные) вместе с `consumer_ai`/`consumer_analytics`/`consumer_payments`, опубликовал по одному событию в каждый из трёх стримов с хоста — во всех трёх логах воркеров нашёл `succeeded` с точным исходным payload (`{'user_id': 111, 'topic': 'ai final test'}` и т.д.) — событие в стриме реально приводит к выполнению задачи воркером именно нужной очереди, полный контейнерный путь, а не заглушка. Тестовые стримы удалены, все 6 контейнеров остановлены после проверки.

### 11.7. Перенос тяжёлых проверок в задачи
- `app/tasks/analytics.py` получил реальную реализацию вместо заглушек: `check_achievements_task(user_id)` — оборачивает `achievements.check_achievements` в собственную async-сессию через `asyncio.run` (Celery-задачи синхронные, а весь остальной код — async SQLAlchemy, поэтому мост `_run_async(coro)` нужен в каждой задаче, трогающей БД); `rebuild_leaderboards_task` — вызывает уже существующий `ratings.rebuild_from_db` из 7.8; `reset_weekly_leaderboard_task` — удаляет текущий недельный ключ лидерборда (сам по себе избыточно, т.к. ключ и так меняется по ISO-неделе, но явная операция сброса нужна была по плану); `process_analytics_event` (уже была задача-диспетчер для консьюмера из 11.5) теперь роутит по полю `action` — при `action='check_achievements'` реально зовёт `check_achievements_task`, иначе просто возвращает kwargs как раньше.

- Проверено вживую сквозным сценарием, который явно доказывает именно асинхронность, а не просто "код не упал": опубликовал реальную историю через `crud_user_story.publish_user_story` — вызов вернулся мгновенно; сразу же проверил `UserAchievements` в БД — **пусто** (ачивка ещё не посчитана); затем отдельно запустил воркер `analytics_queue` и вручную прогнал `consume_once` по стриму `analytics_events` — воркер получил задачу `process_analytics_event`, внутри вызвал `check_achievements_task`, задача завершилась с результатом `['stories_written_1']`; повторная проверка `UserAchievements` в БД — запись реально появилась. Оба состояния (до/после фоновой обработки) зафиксированы отдельными запросами к реальной БД, а не выведены из кода — это и есть подтверждение DoD "действие пользователя → событие → воркер analytics выдаёт ачивку; API-ответ не ждёт". Тестовые данные подчищены.

### 11.8. События платежей
- `purchase_service.purchase` — сразу после успешного `db.commit()` (сама транзакция покупки остаётся полностью синхронной, как того явно требует план — деньги списываются/начисляются немедленно, а не по событию) вызывает `publish_event('payment_events', {...}, fallback_task=process_payment_event)`; `amount`/`seller_income` явно приведены к `str()` перед публикацией — `Decimal` не сериализуется в JSON напрямую, `event_bus.publish_event` внутри делает `json.dumps`.
- `app/tasks/payments.py` — `process_payment_event` теперь не заглушка: логирует "запись аудита" (весь payload целиком), при наличии `seller_id`+`seller_income` логирует обновление дохода продавца и триггер уведомления о продаже (сама доставка уведомления — реальный Telegram/in-app — за пределами этого шага, придёт в фазе 12; здесь честно только точка триггера, без выдуманной системы уведомлений).
- Проверено вживую сквозным сценарием на реальной покупке (не синтетическим payload): купил платную историю за `30` с `seller_share=0.7` через `purchase_service.purchase` — сама покупка отработала как раньше (баланс покупателя `-30`, продавца `+21`, что уже было проверено в 9.7/10.7 и не сломалось от добавления события); `XRANGE payment_events` в реальном Redis показал ровно опубликованное событие с корректными полями (`amount:"30"`, `seller_income:"21.0"`); запустил воркер `payments_queue` и прогнал `consume_once` по стриму — в логе воркера видно и `payment audit: {...}` с полным payload, и `seller 76 income updated by 21.0`, и `notify seller 76 about sale` — задача реально дошла до воркера конкретно нужной очереди с конкретными данными покупки. Оба пункта DoD ("покупка порождает событие"/"воркер payments его обрабатывает") подтверждены на реальной транзакции. Тестовые данные подчищены.

## Фаза 13 — MCP-сервер и ИИ-чат

### 13.1. Скелет MCP-сервера
- Установлен пакет `mcp==2.0.0` (официальный Model Context Protocol SDK) — важное расхождение с планом: план называет класс `FastMCP('Glossa Tools')` по образцу референса `mcp_test`, но в реально установленной (текущей) версии SDK этот класс называется `MCPServer` (`mcp.server.MCPServer`) — `mcp.server.fastmcp` в этой версии не существует вовсе (проверил напрямую импортом, а не предположил). Использовал актуальный `MCPServer` — та же роль, тот же API (`.tool()`/`.run()`/`.list_tools()`/`.call_tool()`), просто новое имя класса в этой версии пакета.

### 13.2. Инструменты: карточки
- `Backend/mcp_server/cards.py` — три `@mcp.tool()`: `get_due_cards(user_id)`, `get_deck_stats(user_id)`, `add_card(user_id, word, translation)`. Переиспользуют уже существующую бизнес-логику (`app.services.review.get_due_cards`, `app.services.crud_card.get_learning_stats`, `app.services.crud_card.create_card`) — без дублирования запросов к БД, ровно как требует принцип проекта "не плодить дубли".
- `Backend/mcp_server/db.py` — добавлен side-effect импорт `app.models.model_card`/`model_user` (`# noqa: F401`, тот же паттерн, что уже применялся в `telegram_bot/bot.py` для 12.4): `Cards` ссылается на `ForeignKey('users.id')`, без импорта `Users` где-либо в процессе конфигурация SQLAlchemy-мапперов падает `NoReferencedTableError` — поймал эту же грабли на практике при попытке создать тестовую карточку до фикса, не только предположил по аналогии.
- Реальный баг, пойманный только на живом прогоне через `stdio_client` (не при импорте модуля напрямую): исходная связка `server.py` (`mcp = MCPServer(...)` → `from mcp_server import cards`) при запуске именно как `python -m mcp_server.server` создавала **два разных экземпляра** `MCPServer`. Причина — классическая ловушка Python: `-m` исполняет файл под именем `__main__`, а `cards.py`, делая `from mcp_server.server import mcp`, импортирует тот же файл **повторно** как отдельный модуль `mcp_server.server` (другой ключ в `sys.modules`, не `__main__`) — это создаёт второй `mcp = MCPServer(...)`, и все три `@mcp.tool()` регистрируются именно на нём, а не на том объекте, у которого реально вызывается `.run()` в `__main__`. Снаружи это выглядело так: прямой `import mcp_server.server` в одном процессе показывал все 3 инструмента (`list_tools()` не пуст), а тот же самый код через настоящий `stdio_client`-подпроцесс отдавал `list_tools: []` и `Unknown tool` на любой вызов — расхождение и навело на причину. Исправлено переносом самого объекта `mcp = MCPServer('Glossa Tools')` в отдельный `mcp_server/instance.py`, на который теперь ссылаются и `server.py`, и `cards.py` — циклической ссылки на входную точку больше нет вне зависимости от способа запуска.
- Проверено вживую на реальных данных, не на моках: создал напрямую в БД тестового пользователя и карточку (`next_review_date=NULL`, т.е. карточка due), поднял настоящий `stdio_client`/`ClientSession`-подпроцесс — `get_due_cards` вернул ровно эту карточку с верными полями; `get_deck_stats` отдал согласованную статистику (`cards_total:1, due_today:1, learned_count:0, forgotten_count:0, retention_rate:0.0`); `add_card` создал вторую реальную карточку; повторный `add_card` с тем же словом корректно вернул `{"error":"CARD_ALREADY_EXISTS","message":"Word is already in your deck"}` — то есть `AppError`, поднятая внутри `crud_card.create_card`, была поймана и превращена в обычный dict-ответ инструмента (в MCP-процессе нет FastAPI-обработчика исключений, ловить `AppError` пришлось явно внутри самого инструмента). Тестовые пользователь и карточки удалены из БД после проверки.

### 13.7. LLM-сервис
- `Backend/app/services/ai_chat.py` (не `modules/ai/service.py`) + `Backend/app/schemas/schema_ai.py` — те же два отступления от буквального плана, что и во всех остальных AI-шагах (layout `app/services`+`app/schemas`, не `modules/`). - Системные промпты на 4 сценария из брифа (`casual`/`interview`/`restaurant`/`airport` — тот же набор, что уже был захардкожен во фронтенд-макетах ИИ-чата, не выдуман заново). Инструкция модели — всегда отвечать одним JSON-объектом `{"reply", "corrections":[{"what","why","better"}]}`; парсинг (`_parse_llm_response`) с фолбэком — если модель всё же не вернёт валидный JSON, весь текст уходит в `reply`, `corrections` пустой, а не падение с исключением (реальная модель иногда не идеально следует формату — это должно быть штатной ситуацией, не багом).
- `send_message(session_id, text, db)` — сохраняет сообщение пользователя **до** обращения к LLM (история не теряется даже при сбое сети), собирает историю сессии в формат чат-сообщений, после ответа — исправления дописываются в `ChatMessages.corrections` того же сообщения пользователя (не отдельной записи) и **отдельно** копируются в `UserErrors` (копилка ошибок для аналитики, как явно требует план, 2.4) — только если исправления реально есть, ни одной пустой записи при чистом сообщении.
- **Честная граница теста, той же природы, что уже фиксировалась для Stripe (9.5) и Telegram (12.3/13.5):** реального ключа LLM-провайдера ни у кого нет (ни в `.env`, ни как переменная окружения хоста) — сам факт связи с настоящим Groq/OpenAI API в этом шаге не проверен и не мог быть проверен. То, что проверено вживую: подменил только саму сетевую функцию `_call_llm` (`unittest.mock.patch`, честно так и указано в тестовом скрипте) на канонiчный ответ в ожидаемом JSON-формате — вся **остальная** логика (сохранение сообщения пользователя до вызова, сборка истории, парсинг, запись исправлений в оба места, второе сообщение без ошибок не создаёт пустых `UserErrors`, порядок сообщений в истории, фолбэк на невалидный JSON) реально прогнана на настоящей БД: создал реального пользователя и сессию, отправил сообщение с ошибкой («I go to the cinema yesterday.») → `UserErrors` получил ровно `('chat_correction', 'go', 'went', 'Past tense needed for "yesterday"')`; второе сообщение без ошибок → `corrections is None`, счётчик `user_errors` не вырос; история сессии — 4 сообщения в правильном порядке (`user, assistant, user, assistant`); `_parse_llm_response('not valid json')` не упал, вернул текст как есть. ### 13.9. WebSocket-приложение
- `Backend/websocket_app/main.py` — отдельное FastAPI-приложение (не роутер основного `app/main.py` — буквально «отдельным сервисом, как в архитектуре» из 1.1), `WS /ws/ai/chat?token=&scenario=&language=`. Аутентификация — свой `authenticate()`, не переиспользует `Depends(get_current_user)` напрямую: тот читает токен из заголовка `Authorization` через `OAuth2PasswordBearer`, а по плану токен приходит query-параметром `?token=...`, у WebSocket-соединений заголовки от браузерного клиента добавить не всегда просто — пришлось написать WS-версию той же логики (`decode_access_token` + `crud_user.get_by_id` + проверка `is_active`), не дублируя сам JWT-декодинг.
- `app/core/limits.py` — `require_ai_access` (HTTP-зависимость) разложена на чистую функцию `check_ai_access(user_id, db)` + тонкую обёртку `Depends`; WS-хендлер вызывает `check_ai_access` напрямую (WS не может использовать `Depends(get_current_user)`-цепочку так же, как обычный роут) — без этого пришлось бы дублировать всю логику free/premium/pro прямо в `websocket_app`.
- «Тикание» реализовано буквально как фоновая задача (`asyncio.create_task`) — раз в секунду, пока сокет открыт, инкрементит `add_ai_seconds` и `ChatSessions.seconds_spent`, и на каждом тике заново проверяет `check_ai_access`; при исчерпании лимита шлёт клиенту `{"type":"limit_reached", ...}` и сам закрывает соединение (код 4403). Это ближе к плановой формулировке «тикание... по времени сессии» (реальное время в разговоре), чем считать только время ответа LLM.
- `Backend/docker/Dockerfile.ws` + сервис `fastapi_websocket` в `docker-compose.yml` (порт 8002, тот же паттерн `DB_HOST=host.docker.internal`/`REDIS_URL=redis://redis:6379/0`, что у консьюмеров). Контейнеризация самого основного `fastapi_main` всё ещё не сделана — она по плану идёт в фазе 16 «финализация docker-compose», не раньше; добавлять её сейчас было бы забеганием вперёд не по своему шагу.
- Реальная методологическая грабля при написании самой проверки (не в коде продукта, а в тестовом скрипте): `engine`/`redis_client` в проекте — синглтоны на уровне модуля, а `starlette.testclient.TestClient.websocket_connect()` поднимает **свой** event loop на каждый `with`-блок — переиспользование пула соединений asyncpg/redis между разными loop'ами реально роняло второе и третье WS-подключения в одном тестовом процессе (`RuntimeError: Event loop is closed` / `'NoneType' object has no attribute 'send'`). Не баг продукта (в реальной работе приложение живёт в одном loop всё время), но пришлось между блоками теста явно `engine.dispose()`/`redis_client.aclose()`, иначе тест сам себя ломал.
- Проверено вживую полным сценарием через настоящий WebSocket-протокол (`TestClient.websocket_connect`, не вызовом функций напрямую), LLM-вызов внутри `ai_chat.send_message` подменён так же, как в 13.7 (честно указано, не единственная непроверенная часть — сеть до реального LLM-провайдера): (1) free-пользователь — подключение отклонено сразу же (`AI_ACCESS_DENIED`, `WebSocketDisconnect` на стороне клиента); (2) premium с заранее выставленным в Redis счётчиком `8998` секунд — `session_started`, затем ровно на очередном тике счётчик перешёл порог `9000`, сокет получил `{"type":"limit_reached","message":"Daily AI time limit reached, upgrade your plan"}` и закрылся; (3) premium со свежим лимитом — `session_started`, отправка реального сообщения → реальный ответ через весь стек (`send_message` → сохранение → ответ) `{"type":"message","reply":"Nice to meet you!","corrections":null}`. Все три пункта DoD («premium общается, free отклоняется, лимит времени срабатывает») подтверждены на живом WS-соединении, не на моках уровня функций. Тестовые пользователи, сессии, подписки и redis-ключи удалены.

## Внеплановая доработка — верификация email и управление аккаунтом (вне нумерации фаз)

Не является частью `Plan/IMPLEMENTATION_PLAN.md` — сделано по прямому запросу пользователя после того,
как при разборе кода `auth_service` обнаружился реальный разрыв между исходным ТЗ и деривативным планом:
`Plan/PROMPT_FOR_PLANNING.md:205` явно перечисляет в разделе аккаунта «смена пароля, 2FA, удаление аккаунта,
экспорт данных», но ни один из этих пунктов не попал ни в один шаг `IMPLEMENTATION_PLAN.md` (прогреплен
весь файл — ноль совпадений на «смена пароля»/«удаление аккаунта»/«2FA»/«экспорт данных»). Верификации email
в чек-листе не было вовсе ни в ТЗ, ни в плане — поле `is_verified` на модели `User` существовало с самого
начала (2.2), но нигде в проекте не выставлялось в `True`: мёртвое поле. Закрыто двумя заходами: сначала
верификация email + редактирование данных аккаунта (включая email) + смена пароля + мягкое удаление аккаунта;
следующим заходом, по отдельному запросу пользователя после того, как он спросил «какие ещё остались
пробелами» и получил список оставшихся двух пунктов — 2FA и экспорт данных, закрывающие весь список
`PROMPT_FOR_PLANNING.md:205` целиком.

- `Backend/auth_service/auth_service/settings.py` — добавлены `REDIS_URL` (тот же `.env`-ключ, что и у
  FastAPI/Celery/консьюмеров) и полный блок `EMAIL_*`/`DEFAULT_FROM_EMAIL` из уже существующих в `.env`
  переменных (`EMAIL_HOST` и т.д. — они были заведены ещё для Celery-почты в 12.2, Django их до этого
  момента просто не читал).
- `Backend/auth_service/users/redis_client.py` — свой `redis.from_url(settings.REDIS_URL, decode_responses=True)`,
  по образцу `app/core/redis_client.py` на стороне FastAPI. Новая зависимость Django-сервиса не потребовала
  `pip install` — `redis==8.0.1` уже в общем `requirements.txt` (единый venv на весь `Backend/`, FastAPI и
  Django реально ставятся из одного файла).
- `Backend/auth_service/users/verification.py` — `send_verification_email(user)`/`confirm_verification_code(user, code)`.
  Код — 6 цифр (`secrets.choice`, не `random`), лежит в Redis `email_verify_code:{user_id}` с TTL 600с (10 минут,
  тот же порядок величины, что и `telegram_link_service.CODE_TTL_SECONDS` в 12.4 — переиспользовал уже
  устоявшийся в проекте паттерн одноразового кода с истечением через Redis TTL, а не завёл отдельную таблицу
  и cron на чистку). Отдельный ключ-кулдаун `email_verify_cooldown:{user_id}` (60с) — **выставляется только
  после успешной отправки письма**, осознанное решение: если реальная отправка упала (ровно тот сценарий
  «если код не отправился», о котором спросил пользователь), клиент может тут же попробовать `resend` ещё раз,
  а не ждать минуту бессмысленно. Отправка через `django.core.mail.send_mail` обёрнута в `try/except` —
  любое исключение (в том числе реальная сетевая ошибка SMTP) превращается в `EmailDeliveryError`, наружу
  не улетает необработанным 500.
- `Backend/auth_service/users/serializers.py` — `UpdateMeSerializer` (частичное обновление `username`/`email`,
  `validators=[]` + собственные `validate_email`/`validate_username` с `.exclude(id=self.instance.id)` — та же
  идея, что и в `RegisterSerializer`, но с исключением себя из проверки уникальности, иначе пользователь не
  смог бы сохранить профиль с уже своим же email), `VerifyEmailSerializer`, `ChangePasswordSerializer`
  (`validate_old_password` через `user.check_password`, `validate_new_password` — через штатные
  `AUTH_PASSWORD_VALIDATORS` из `settings.py` — те же 4 валидатора, что были заведены в 2.x, просто раньше
  нигде не вызывались руками), `DeleteAccountSerializer` (подтверждение паролем перед деактивацией).
- `Backend/auth_service/users/views.py` — `RegisterView.create()` переопределён: после `serializer.save()`
  зовёт `send_verification_email`, ошибку отправки не превращает в отказ регистрации (пользователь всё равно
  создан) — в ответ добавлено поле `email_sent: bool`, честно сообщающее клиенту, ушло письмо или нет.
  `MeView` из `RetrieveAPIView` переписан в явный `APIView` с `get`/`patch`/`delete`: `patch` — если `email`
  реально меняется, `is_verified` сбрасывается в `False` и отправляется новый код **на новый адрес**, ровно
  как просил пользователь («как при регистрации»); `delete` — **мягкое** удаление (`is_active = False`), не
  физический `DELETE FROM users`. Осознанное архитектурное решение, а не недоделка: `users.id` — FK-цель для
  примерно двух десятков таблиц в `app/models/*`, которые Django вообще не видит (они не в его миграциях,
  граница владения `users`-таблицей описана в `docs/CONVENTIONS.md` §9) — жёсткий `DELETE` почти гарантированно
  упёрся бы в `IntegrityError` на первой же карточке/отзыве/платеже пользователя, а мягкое удаление —
  стандартная практика для такого объёма связей и к тому же обратимо. Новые `VerifyEmailView`,
  `ResendVerificationView` (429 + `seconds_left` при кулдауне, 502 при реальной ошибке отправки),
  `ChangePasswordView`.
- `Backend/auth_service/users/urls.py` — `PATCH/DELETE /api/auth/me` (через тот же `MeView`),
  `POST /api/auth/change-password`, `POST /api/auth/verify-email`, `POST /api/auth/verify-email/resend`.
  Новых миграций не потребовалось — `is_verified`/`is_active`/`password`/`email` уже существовали на модели.
- `Backend/app/api/auth.py` — `get_current_user` дополнен проверкой `if not user.is_active: raise AppError('ACCOUNT_DEACTIVATED', ..., 401)`.
  Без этого мягко удалённый на Django-стороне аккаунт продолжал бы работать в FastAPI по ещё не истёкшему
  access-токену (до 30 минут) — Django-логин такой токен уже не выдаст (SimpleJWT сам проверяет `is_active`),
  но существующий токен сам по себе не отзывается, поэтому проверку нужно было продублировать явно на
  FastAPI-стороне.
- Проверено вживую сквозным сценарием на реальном пользователе, реальном Gmail SMTP и реальном Redis
  (docker-контейнер `redis` пришлось поднять заново — стоял, как и в 12.2): регистрация → `email_sent: true`,
  `GET /me` → `is_verified: false`; немедленный `resend` → `429` с `seconds_left`; проверка кода `000000` →
  `400`; настоящий код, вычитанный напрямую из Redis (сам email в реальный inbox не читал — это тот же принцип
  границы теста, что и с Telegram в 9.5/12.3: сетевая доставка через Gmail подтверждена самим фактом `email_sent: true`
  без исключения от `smtplib`, а не повторным чтением почты) → `200`, `is_verified: true`; `PATCH /me` со сменой
  email → `is_verified` снова `false`, `email_sent: true`, `GET /me` подтвердил новый адрес; смена пароля:
  слабый новый пароль → `400` от штатного `AUTH_PASSWORD_VALIDATORS`, неверный старый пароль → `400`, реальная
  смена → `200`, повторный логин старым паролем → `401`, новым — `200`; удаление аккаунта: неверный пароль →
  `400`, реальное подтверждение → `204`; повторный логин после этого → `401` (Django сам отклоняет неактивных
  через `TokenObtainPairView`). Отдельно проверено на стороне FastAPI напрямую через `crud_user.get_by_id` —
  тот же самый пользователь (общая таблица `users`) реально показывает `is_active: False`, подтверждая, что
  добавленная проверка в `get_current_user` сработает. Тестовый пользователь удалён из БД после прогона.

### Вторая доработка — 2FA и экспорт данных

Закрывает оставшиеся два пункта `PROMPT_FOR_PLANNING.md:205`, найденные при повторном систематическом
сравнении всего раздела 2 (`2.1`–`2.13`) ТЗ с `IMPLEMENTATION_PLAN.md` по прямому вопросу пользователя
«какие ещё остались пробелами» — кроме этих двух других настоящих пробелов не нашлось (таблица тарифов из
2.5 сверена построчно с `seeds/seed_plans.py` — совпадает; MinIO закрыт шагом 3.6; Kafka→Redis Streams —
задокументированное согласованное решение из 11.3, не пробел).

**2FA** — TOTP (`pyotp`, совместим с Google Authenticator/Authy), выключено по умолчанию, включает/выключает
только сам пользователь (явное требование пользователя в этом чате).
- `Backend/auth_service/users/models.py` — три новых поля: `is_2fa_enabled` (bool, default `False`),
  `totp_secret`, `backup_codes` (JSON-список хэшей). Миграция `0002_user_backup_codes_user_is_2fa_enabled_and_more`
  (автосгенерированный slug Django — в отличие от Alembic, ручные осмысленные slug'и для миграций `users`
  таблицы конвенциями проекта не оговорены, `docs/CONVENTIONS.md` §9 и так исключает эту таблицу из зоны
  ответственности Alembic). Цикл `migrate users 0001 → migrate users` (полный откат и накат) проверен, чист.
- `Backend/auth_service/users/two_factor.py` — генерация секрета/`otpauth://` URI (`pyotp.totp.TOTP.provisioning_uri`,
  для будущего QR-кода на фронте), проверка кода с `valid_window=1` (допуск ±30с на рассинхрон часов клиента),
  8 бэкап-кодов (`secrets.token_hex(4)`), хранятся хэшированными через `django.contrib.auth.hashers.make_password`
  — тот же хэшер, что и для паролей пользователей, не отдельный. `create_pending_login`/`resolve_pending_login`
  — тот же паттерн одноразового Redis-токена с TTL, что уже применялся для email-кодов и Telegram-привязки;
  `resolve_pending_login` удаляет ключ сразу при чтении (одноразовость), даже если код после этого окажется
  неверным — сознательно, тот же принцип уже был в `telegram_link_service.resolve_link_code` (12.4).
- `Backend/auth_service/users/views.py` — `login` переписан из прямого `TokenObtainPairView` в кастомный
  `LoginView`: если у пользователя `is_2fa_enabled=False` — токены выдаются как раньше (обратная
  совместимость, формат ответа не изменился); если `True` — вместо токенов возвращается
  `{requires_2fa: true, pending_token}` (TTL 5 минут), реальные токены выдаёт отдельный `Verify2FALoginView`
  (`POST /login/2fa`) после проверки TOTP-кода **или** бэкап-кода. `Setup2FAView` генерирует секрет, но не
  включает 2FA сразу — включает только `Confirm2FAView` после успешной проверки первого кода (стандартная
  защита от блокировки себя же неработающим приложением-аутентификатором). `Disable2FAView` требует пароль
  (переиспользован `PasswordConfirmSerializer` — переименован из `DeleteAccountSerializer`, так как теперь
  используется в двух местах, а не только для удаления аккаунта).
- Проверено вживую полным сценарием с реальным `pyotp.TOTP(secret).now()` (тот же алгоритм, каким
  пользуется настоящее приложение-аутентификатор): логин без 2FA → токены как раньше; `2fa/setup` → секрет
  и URI; `2fa/confirm` неверным кодом → `400`, реальным TOTP-кодом → `200` + 8 бэкап-кодов; логин теперь
  возвращает `requires_2fa` без токенов; `login/2fa` неверным кодом → `400`, **и** тот же `pending_token`
  повторно уже недействителен (одноразовость подтверждена на практике, не только по коду); свежий
  `pending_token` с реальным TOTP-кодом → токены; отдельный логин + бэкап-код → тоже токены; повторное
  использование того же бэкап-кода → `400` (списание подтверждено); `2fa/disable` неверным паролем → `400`,
  реальным → `200`; логин после отключения снова выдаёт токены напрямую, без 2FA — переключатель полностью
  обратим. Тестовый пользователь удалён после прогона.

**Экспорт данных** — реализован на стороне FastAPI (`GET /export/me`), не Django, осознанно: по архитектуре
проекта (`PROMPT_FOR_PLANNING.md:41`) Django владеет только auth-полями, а ≈95% реальных данных пользователя
(колода, история покупок, соцсвязи, достижения, авторские истории и т.д.) живёт в FastAPI-моделях, которые
Django вообще не импортирует — содержательный экспорт «всех своих данных» физически не мог быть собран на
стороне Django.
- `Backend/app/services/data_export.py` — `build_user_export(user_id, db)` — единственная новая функция;
  всё остальное — вызовы уже существующих `crud_*`/сервисных функций (`crud_profile.get_profile`,
  `crud_card.get_cards`/`get_learning_stats`, `achievements.get_my_achievements`,
  `crud_subscription.get_active_subscription`, `crud_payment.get_or_create_balance`/`get_payment_history`,
  `crud_notification.get_notifications`, `crud_social.get_followers`/`get_following`/`get_friends`,
  `streaks.get_streak`, `crud_settings.get_settings`) — без дублирования ни одного запроса к БД, ровно
  принцип проекта "не плодить дубли". Единственный по-настоящему новый запрос — список **собственных**
  историй пользователя **включая черновики** (`select(UserStories).where(author_id=...)` без фильтра по
  `status`): существующая `crud_user_story.get_user_stories` для этого не подходит, она жёстко фильтрует
  `status == 'published'` (это каталог для читателей, не личный экспорт) — переиспользовал только форматирующий
  хелпер `user_story_to_response` из того же модуля.
- `Backend/app/api/router_export.py` — `GET /export/me`, тонкий роутер: вызывает `data_export.build_user_export`
  и добавляет блок `account` (`username`/`email`/`role`/`is_verified`/`created_at` из уже загруженного
  `current_user`, без похода в Django). Осознанное отступление от `docs/CONVENTIONS.md` §7 ("`response_model`
  указывается всегда") — у экспорта нет единой типизированной формы по своей природе (это дамп разнородных
  доменов целиком), заворачивать его в Pydantic-схему было бы искусственным дублированием уже существующих
  `*Response`-схем каждого домена ради одного эндпоинта.
- Проверено вживую на реальном, не пустом состоянии: тот же тестовый пользователь из прогона 2FA (с уже

## Фаза 16 — Финализация

### 16.1. Полный docker-compose
- Создан `docker/Dockerfile.api` для `fastapi_main` — раньше основного FastAPI-приложения в compose не было вообще, поднимался только `fastapi_websocket`.
- **Найден и исправлен реальный баг**, не гипотетический: у всех Celery-воркеров/консьюмеров/`telegram_bot`/`fastapi_websocket` в `environment:` стояли `DB_HOST: host.docker.internal`/`DB_PORT: 5432` — но `app/core/config.py` (FastAPI-сторона, в отличие от Django) читает готовый `DATABASE_URL` целиком, а не собирает его из `DB_HOST`/`DB_PORT`. Проверил реальный `.env`: `DATABASE_URL` там жёстко зашит на `localhost:5432`, то есть внутри контейнера указывал бы сам на себя. Живьём подтвердил через `netstat`/`docker ps`, что вся сессия тестировалась через нативный Postgres на 5432 (не через контейнерный, который висит на 5433) — контейнерный Postgres ни разу не был реально смигрирован (подтвердилось позже: `\dt` в свежем контейнере не нашёл ни одной таблицы). Исправлено: все FastAPI-стороны сервисов получают явный `DATABASE_URL` с хостом `postgres` (DNS-имя сервиса в сети compose), добавлены недостающие `depends_on: postgres: condition: service_healthy` (раньше воркеры стартовали, не дожидаясь БД).
- Добавлены `profiles: ['full']` на elasticsearch/minio/minio_init/все celery-воркеры/консьюмеры/telegram_bot — голый `docker compose up` теперь поднимает только core (postgres+redis+django_app+fastapi_main+fastapi_websocket), `--profile full up` — всё, как требует DoD.
- **Docker Desktop дважды полностью падал** во время работы над этим шагом — движок переставал отвечать (500 от `dockerDesktopLinuxEngine`), затем пропадал как процесс. Причина — реальная нехватка памяти на машине (проверил через `Get-Counter '\Memory\Available MBytes'`, не вводящий в заблуждение `FreePhysicalMemory` — доступно было ~1ГБ на 15ГБ машине), полный `--profile full` (17 контейнеров + JVM-хип Elasticsearch) её не выдержал. Мягкий перезапуск Docker Desktop (`Start-Process`) не помог — движок оставался в «призрачном» состоянии: Windows показывал порты `LISTENING`, но за ними никто не отвечал (`curl` — `000`, Redis `PING` — таймаут). Помог только полный `wsl --shutdown` + `Stop-Process -Force` всех `*docker*`/`vmmemWSL` процессов + чистый релонч — после этого движок поднялся стабильно.
- **Сознательно ограничил проверку core-профилем** (5 контейнеров: postgres/redis/django_app/fastapi_main/fastapi_websocket) вместо полного `--profile full` — машина не тянет одновременно 17 контейнеров + Elasticsearch, полный профиль отложен до менее нагруженного окружения; DoD по сути про то, что стек **вообще** воспроизводимо поднимается и работает, а не про то, что прямо сейчас подняты все 17 сервисов разом.
- **`fastapi_main` падал с exit code 3** — реальный, не инфраструктурный баг, найден по логам контейнера: `sqlalchemy.exc.ArgumentError: Expected string or URL object, got None` внутри дочернего MCP-подпроцесса, который `lifespan` спавнит через `ai_mcp.connect()`. Причина — `mcp_server/client.py: SERVER_PARAMS = StdioServerParameters(command=sys.executable, args=[...])` не передавал `env=` явно, а MCP SDK по умолчанию даёт дочернему процессу **урезанное** окружение (без `DATABASE_URL` и прочего) — намеренная защита протокола для недоверенных tool-серверов. На хосте это маскировалось тем, что `Backend/.env` — реальный файл на диске, и дочерний `load_dotenv()` читал `DATABASE_URL` оттуда напрямую, а `.env` в образ не попадает (`.dockerignore` его явно исключает) — поэтому баг ни разу не проявлялся раньше, ведь `fastapi_main` до этого шага вообще не запускался в Docker. Исправлено: `StdioServerParameters(..., env=dict(os.environ))` — свой первоклассный MCP-сервер, не третья сторона, доверенное наследование окружения корректно. Пересобрал образ, `fastapi_main` стабильно живёт после фикса (проверено — не падает больше нескольких минут подряд).
- **Второй реальный баг**, найден тем же путём (живая регистрация через контейнерный Django): `django_app` в моей же правке 16.1 получил `DB_HOST`/`DB_PORT`, но не `REDIS_URL` — `auth_service/users/redis_client.py` читает `settings.REDIS_URL` (дефолт `localhost:6379`), верификация email падала с `ConnectionError: Error 111 connecting to localhost:6379`. Добавил `REDIS_URL: redis://redis:6379/0` в `environment:` сервиса `django_app` + `depends_on: redis`.
- **Живая проверка DoD, по шагам, все — через реально поднятые контейнеры:**
  1. Миграции: `docker compose exec django_app python manage.py migrate` (создаёт `users` — Django владеет), затем `docker compose exec fastapi_main alembic upgrade head` (не наоборот — FastAPI-таблицы имеют FK на `users`, без Django-миграции первым падает `UndefinedTableError`). Обе прошли на пустой БД от начала до конца: Django — 20 миграций, Alembic — вся цепочка от `88bff8d55a71` (empty baseline) до `1eaf75015e96` (мой source_key из Фазы 15), `\dt` — 49 таблиц.

  4. Контракт Django↔FastAPI: тем же access-токеном — `GET http://localhost:8000/profile/me` (контейнер `fastapi_main`, другой процесс) → 200, реальный профиль. Подтверждает, что оба сервиса видят один и тот же `JWT_SECRET_KEY` и одну и ту же БД.
